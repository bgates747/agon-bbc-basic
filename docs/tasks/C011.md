## Experimental design

1. Use one numbered conventional BASIC source per case under both engines,
   identical fixed inputs and work counts. Supply deterministic tables rather
   than RND. Setup, timed kernel and post-run validation are distinct phases.
   A runtime-loaded operand prevents a literal-only optimisation demonstration
   from masquerading as arithmetic throughput. Retain generated code inspection
   for unexpectedly large gains.
2. Cross control structure with arithmetic density: repeat the same branch,
   loop and access pattern with a small, medium and large number of dependent
   numeric operations per iteration. Run separate integer and float40 families,
   with bounded values and documented promotion. Conversely hold arithmetic
   work fixed while varying branch/call/variable-access frequency. Neither
   experiment is a pure decomposition: expression evaluation and operand access
   also cost time, and changing source changes interpreter traversal.
3. Vary symbol/name-table size and branch target distance separately. Exercise
   always-taken, never-taken and deterministic mixed paths. Avoid conflating
   float arithmetic with integer loop bounds, and do not presume integer work
   is cheap: division, multiplication and promotion need separate cases.
4. Use useful output and verified final values. A lightweight state update
   belongs inside the timed kernel when needed to preserve work; perform the
   full checksum outside it. Reset state identically for every repetition.
5. Report each kernel separately. Plot reference and compiled time per unit
   of work against arithmetic density, plus speedup and uncertainty. Similar
   slopes with a lower compiled intercept would support the overhead hypothesis;
   different slopes require investigation rather than automatic attribution.
   Reference-minus-native time is a net difference, not an exact measurement of
   interpreter time: generated code, operand handling and runtime glue differ.

## Timing and attribution

1. Inspect MOS/target timer interfaces and available emulator counters before
   selecting the harness. TIME is not currently an admitted compiler feature;
   do not silently put it in fixture source. Prefer a small external target
   harness that records identical start/end boundaries for both engines.
   If necessary, use an identical pinned harness hook in both paths, separately
   qualified and accounted for; do not widen CALL/USR or TIME support implicitly.
   The first fixture exports the MOS sysvars pointer via clock.bin and uses
   existing read-only BASIC indirection, with bounded double sampling.
2. Verify actual timer granularity, update behavior, wrap and read consistency.
   Millisecond resolution is helpful but not required for throughput: batching
   ten seconds makes a 10 ms tick about 0.1% of elapsed time, before other error.
   Calibrate untimed, freeze the same count for both engines, and choose longer
   batches if quantisation/variance prevents resolving the difference.
3. Timer boundaries must exclude compilation, loading, data preparation, final
   reporting and GET waits for kernel results. A coarser whole-program timing
   includes those costs explicitly and is reported separately. Benchmark the
   timing mechanism and empty harness, retain its cost, and report raw times;
   subtraction is supplementary, never the sole result.
4. One warmup, then at least five measured runs per engine, alternating order
   and resetting state. Preserve all ticks, failures, medians and spread; add
   repeats only for a documented precision/variance need. Use the same physical
   Console8 configuration for physical comparisons. Any other hardware needs
   its own current authorization/custody; this plan reserves no bench.
5. For stronger causal attribution, first inspect whether the emulator exposes
   trustworthy instruction/cycle counts and address-range tracing. If available,
   map qualified reference/runtime symbols and count time/cycles in shared
   arithmetic bodies versus remaining code, including nested calls without
   double counting. Static CALL counts alone do not measure numeric cost.
   If unavailable, retain matched-kernel evidence and explicitly label causal
   attribution as inference. Host emulator wall time is not Agon speed.
6. I/O/display cases retain device-completion and cache-state limitations.
   Keyboard/line-editor cases use scripted input for correctness; interactive
   demonstrations and deliberate wait times receive no CPU-speed score.

## Acceptance and disposition

1. Every implemented/partial compatibility row has a justified coverage entry;
   unsupported constructs are excluded explicitly, never silently replaced.
2. Both engines pass exact result/output checks before a sample is admitted.
   Preserve source/input/image hashes, reference/compiler/runtime revisions,
   target/MOS/VDP/SD configuration, work counts, timing boundaries, clock evidence
   and all raw samples in fresh immutable cohorts.
3. Publish per-family timings and uncertainty, arithmetic-density comparisons,
   selected application results and clear limits on attribution. Do not collapse
   unlike workloads into an unsupported universal speedup.
4. Implementation, automated qualification, physical measurement and human
   acceptance remain distinct. Promote a reusable suite only after its actual
   correctness/timing evidence exists. This tranche changes no live compiler,
   interpreter or runtime, and supplies no precompiled BASIC benchmark image.
