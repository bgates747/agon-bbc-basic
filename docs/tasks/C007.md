# C007 — Curated correctness and performance program search

Build a source-backed shortlist of BASIC programs for correctness testing and
performance comparisons. Cover interpreter-heavy execution as well as numeric
and device-heavy controls, so future compiler results explain where time goes.
This task searches and classifies programs; it does not claim measured speedups.

## Scope

1. Inventory existing correctness, regression and timing programs in the local
   BASIC repositories. Search primary external repositories/documentation for
   additional established benchmarks and realistic programs.
2. Classify candidates by statement/branch dispatch, variable access, loop
   handling, GOTO/GOSUB, PROC/FN/LOCAL, strings, arrays, parsing, integer work,
   floating point, file/console I/O and mixed applications.
3. Prioritise workloads that expose interpreter overhead: branch decisions,
   calls, variable lookup, string/record processing and small operations.
   Include arithmetic-heavy and device-heavy controls for comparison.
4. For each shortlisted item record its exact source/revision, license or
   reuse uncertainty, language dependencies, correctness oracle, adaptation
   requirements, likely bottleneck and suitability for the current compiler
   versus future feature stages.
5. Define a reproducible measurement protocol: equal work, deterministic input,
   output/checksum validation, timed regions, warmups/repeats, timer resolution,
   output/device isolation and versioned hardware/interpreter/compiler inputs.
   Distinguish semantic tests, microbenchmarks and realistic workloads.
6. Identify gaps requiring later authored/adapted benchmarks without silently
   beginning compiler feature work or reporting proposed cases as existing
   programs. Keep involved scripts/experimental data in `docs/tasks/C007/`.

## Acceptance criteria

1. A curated catalogue links to inspected sources and explains selection or
   rejection rather than listing names found by search alone.
2. The recommended suite covers control flow and interpreter-sensitive work,
   integer/float controls, I/O boundaries and at least one realistic mixed
   workload. It identifies missing coverage honestly.
3. Every selected candidate has an oracle and adaptation/eligibility assessment,
   with license/provenance recorded. A passing reference test is not presented
   as a passing compiler test.
4. Measurement guidance explains why shared arithmetic routines and MOS/VDP/SD
   time can limit visible gains, and how to distinguish those costs from
   dispatch/parser/lookup overhead. No unmeasured speedup is asserted.
5. The task record and dated development log retain findings and disposition.
   Any intentionally promoted follow-on implementation remains in the single
   root TODO; the catalogue does not create a competing task checklist.
